# Slice 0 implementation notes

- Better Auth 1.7.7 owns Google OAuth, state/CSRF validation, cookie signatures and revocable database sessions. Google email must be verified and pre-approved. No password login, account linking or provider-token persistence. Database hooks strip OAuth credentials; SQL constraints reject accidental persistence.
- Approval uses normalized verified Google email. Provider/subject identity remains unique in Better Auth's account table. `app_users` stores shared-team approval and admin/analyst/viewer roles. Protected handlers/pages must call `currentUser()` on every request. Never authorize with a cached session role. The database runtime cannot change approvals or create tables; operator approval uses the migration credential.
- The plan's illustrative custom auth tables are replaced with the maintained library's native schema. Better Auth stores opaque session tokens in its session table (not the illustrative SHA-256 column). No custom token or crypto implementation was introduced. Keep database credentials restricted; sessions expire after one day, cookie caching is disabled, and disabling a user deletes their sessions. Cookie defaults are HttpOnly/SameSite=Lax and Secure with HTTPS.
- `monitor` schema stores timestamps as `timestamptz`; application connections use UTC. Display timezone will be Asia/Dhaka. `pg_trgm` is installed for later slices. No future-slice business tables are created.
- One transactional up/down migration belongs to slice 0. Migrator provisions `monitor_runtime` and grants auth-table DML and approval SELECT. Runtime has no schema CREATE or approval mutation rights. Migration ledger is outside the app schema and inaccessible for runtime writes. Use separate migration/runtime URLs. Keep local env files ignored.
- Tailwind is configured. shadcn/ui components will be added when a slice requires them; slice 0 has only sign-in and workspace status.
- Tests cover approval, verified email, disabled accounts, role policy, live authorization, library session creation/revocation, token stripping, schema compatibility, FKs/check constraints and restricted credentials. Google redirect flow requires real OAuth credentials and a browser; synthetic tests do not claim to verify Google itself.

## Validation performed

Fresh migration, repeated migration, rollback/reapply, integration tests, unit tests, typechecks and production build passed against a real PostgreSQL 18.6 server. Production web smoke returned 200 for `/`, 401 for signed-out `/api/me`, and a null auth session. Worker started successfully against PostgreSQL and a real Redis 8.0.5 server and was shut down after the check. Library-issued signed cookies were verified and rejected after session revocation. Docker is unavailable in this build environment, so Compose execution itself was not verified; pinned Docker image tags were checked against the registry. Real Google OAuth sign-in still requires operator credentials.
